# Peekaboo & the local computer-use layer — deep dive

Date: 2026-07-06. Scope: Peekaboo (macOS screen capture + UI automation), its role as our **local computer-use exploratory-test round**, and the cross-OS/cloud fallback matrix (cua, Anthropic computer-use reference, Playwright).

---

## 1. What Peekaboo is

Peekaboo is a **macOS CLI + optional MCP server + menu-bar app** that gives an AI agent eyes (screen/accessibility capture) and hands (click/type/scroll/window control) on a real Mac desktop. Author: Peter Steinberger ([@steipete](https://github.com/steipete)). Canonical description from the repo: *"Peekaboo brings high-fidelity screen capture, AI analysis, and complete GUI automation to macOS."* ([github.com/openclaw/Peekaboo](https://github.com/openclaw/Peekaboo))

**Current home:** [github.com/openclaw/Peekaboo](https://github.com/openclaw/Peekaboo) — under the `openclaw` GitHub org (Peter Steinberger's OpenClaw ecosystem org, alongside `crabbox` and `mcporter`, see §6). Older links resolve at `github.com/steipete/Peekaboo` as well; the org page shows `openclaw/Peekaboo` as the live breadcrumb with 4.8k★ / 374 forks / 28 releases, so treat `openclaw/Peekaboo` as canonical and `steipete/Peekaboo` as the legacy/author alias. ([github.com/openclaw/Peekaboo](https://github.com/openclaw/Peekaboo))

Docs site: [peekaboo.sh](https://peekaboo.sh/). One-line self-description there: *"a macOS automation toolkit for humans and agents. It captures pixels, reads the accessibility tree, drives input, and ships an agent runtime plus an MCP server."* ([peekaboo.sh](https://peekaboo.sh/))

### 1.1 Exact capabilities

Full CLI command surface (also the MCP tool surface, see §3): `image`, `see`, `list`, `analyze`, `click`, `type`, `set-value`, `perform-action`, `press`, `hotkey`, `paste`, `scroll`, `swipe`, `drag`, `move`, `window`, `app`, `space`, `menu`, `menubar`, `dock`, `dialog`, `run`, `agent`, `sleep`, `clean`, `tools`, `completions`, `config`, `permissions`, `mcp`. ([github.com/openclaw/Peekaboo](https://github.com/openclaw/Peekaboo), [docs/commands/tools.md](https://github.com/openclaw/Peekaboo/blob/main/docs/commands/tools.md))

- **Capture (`image`, `see`).** Pixel-accurate capture of a screen, window, or the menu bar, with optional Retina 2x scaling. `see` additionally walks the macOS **Accessibility (AX) tree** (configurable `--max-depth` default 12, `--max-elements` default 1000, `--max-children` default 250) and returns a JSON `ui_map`/`ui_elements` list — labels, roles, bounding boxes, a `snapshot_id` — that downstream commands (`click --snapshot …`, `type --snapshot …`) target instead of raw pixel coordinates. Capture uses ScreenCaptureKit (20–100ms) with a CGWindowList fallback; element detection is 200–800ms and can correlate the AX result with a vision-model pass. ([docs/commands/see.md](https://github.com/steipete/Peekaboo/blob/main/docs/commands/see.md), [docs/ARCHITECTURE.md](https://github.com/openclaw/Peekaboo/blob/main/docs/ARCHITECTURE.md))
- **Vision QA (`analyze`, `image --analyze`).** Ask a local or remote vision model a natural-language question about a captured image (multi-provider via the bundled **Tachikoma** provider layer — Anthropic/OpenAI-compatible + local models). ([peekaboo.sh](https://peekaboo.sh/), [ARCHITECTURE.md](https://github.com/openclaw/Peekaboo/blob/main/docs/ARCHITECTURE.md))
- **Input automation.** `click`, `type`, `set-value`, `perform-action` (invoke an AX action directly, e.g. `AXPress`), `press`/`hotkey`/`paste` (keyboard), `scroll`/`swipe`/`drag`/`move` (pointer), each addressable by AX element id, label, or `snapshot_id` + bounding-box center. ([tools.md](https://github.com/openclaw/Peekaboo/blob/main/docs/commands/tools.md))
- **Window/app/space management.** `window` (move/resize/focus/list), `app` (launch/quit/focus), `space` (macOS Spaces/virtual desktops), `menu`/`menubar` (discover and click native menu items), `dock`, `dialog` (system dialog handling). Supports both foreground and background input delivery (can drive an app without stealing focus). ([tools.md](https://github.com/openclaw/Peekaboo/blob/main/docs/commands/tools.md), [ARCHITECTURE.md](https://github.com/openclaw/Peekaboo/blob/main/docs/ARCHITECTURE.md))
- **Scripted verification (`run`).** Executes a `.peekaboo.json` "PeekabooScript" file — a sequence of steps run in order via `ProcessService`, fail-fast by default (`--no-fail-fast` to continue), each step reporting timing/success/error, exit code reflects overall pass/fail for CI use. No built-in assertion DSL beyond step success/failure — verification logic (did the UI reach the expected state) is left to the caller inspecting `see`/`analyze` output. ([docs/commands/run.md](https://github.com/openclaw/Peekaboo/blob/main/docs/commands/run.md))
- **Agent mode (`agent`).** A natural-language plan/act loop that chains the above primitives — e.g. `peekaboo agent "open Safari and search for Peekaboo"` — with resumable sessions ("snapshots") and verbose visual traces. This is the exploratory/autonomous mode; `run` is the durable/scripted mode. ([peekaboo.sh](https://peekaboo.sh/), [WebSearch result](https://github.com/openclaw/Peekaboo))
- **UI-state verification.** No explicit before/after diff primitive is documented; verification is compositional — capture (`see`/`image`) → inspect (`analyze` or read the AX JSON) → assert in the calling harness. Defensive traits noted in the architecture doc: permission validation, 2s timeout protection on element lookups, "element existence and accessibility verification," and an automatic web-focus fallback that re-runs AX traversal if zero text fields are found (form-detection heuristic). ([ARCHITECTURE.md](https://github.com/openclaw/Peekaboo/blob/main/docs/ARCHITECTURE.md), [see.md](https://github.com/steipete/Peekaboo/blob/main/docs/commands/see.md))

### 1.2 Architecture (relevant internals)

Five Swift modules: `PeekabooAutomation` (capture/menu/window/app services over Accessibility + ScreenCaptureKit), `PeekabooAgentRuntime` (MCP tools, `ToolRegistry`, agent service), `PeekabooVisualizer` (on-screen feedback overlay, decoupled), `PeekabooCore` (umbrella/`PeekabooServices` container), and `Tachikoma` (AI provider abstraction). Runtime shapes: a long-lived **daemon** that holds the macOS TCC (Screen Recording/Accessibility) permission grants, the **Peekaboo.app** GUI, or an **MCP server** with process-local services; the CLI resolves in priority order healthy-daemon → capable-app → auto-started-daemon. Depends on submodules `AXorcist` (accessibility wrapper) and `Commander` (CLI argument parsing). ([ARCHITECTURE.md](https://github.com/openclaw/Peekaboo/blob/main/docs/ARCHITECTURE.md))

## 3. MCP surface & how an agent drives it — the important nuance

Peekaboo runs as an MCP **server** (stdio protocol), installable via `npx -y @steipete/peekaboo` or the Homebrew binary's `peekaboo mcp` subcommand, and is compatible with Claude Desktop, Claude Code, Cursor, and Codex as an MCP client. Exposed MCP tools mirror the CLI verb set (`image`, `see`, `click`, `type`, `window`, `list`, plus a dedicated `browser` and `inspect-ui` wrapper for some verbs). `peekaboo tools --json` dumps the live tool catalog for introspection/debugging. ([tools.md](https://github.com/openclaw/Peekaboo/blob/main/docs/commands/tools.md), [WebSearch](https://github.com/openclaw/Peekaboo))

**But the project's own architectural direction is CLI-first, not MCP-first.** In "Peekaboo 2.0 – Free the CLI from its MCP shackles," Steinberger's stated rationale for decoupling:
- MCP tools stay loaded in every agent session (context cost) regardless of whether screen automation is needed that turn.
- "Agents are really, really good at calling CLIs (actually much better than calling MCPs)" — lower latency, and a CLI composes with shell pipelines/scripts in ways MCP tool-calls don't.
- The recommended integration pattern is: mention Peekaboo in `CLAUDE.md`/`AGENTS.md`, and let the coding agent shell out to it on demand (`peekaboo image --app Safari --analyze "..."`) as a stateless utility it can invoke hundreds of times without paying an MCP tax.
([steipete.me/posts/2025/peekaboo-2-freeing-the-cli-from-its-mcp-shackles](https://steipete.me/posts/2025/peekaboo-2-freeing-the-cli-from-its-mcp-shackles))

**Implication for us:** our harness/agent should invoke Peekaboo the same way its own author recommends — as a **CLI subprocess with `--json` output**, not as a standing MCP server we keep wired into every agent context. Keep the MCP path available only for the case where the *human's* IDE agent (Claude Desktop/Cursor) wants interactive access; our automated verify loop should shell out.

## 4. Platform coverage — is it macOS-only?

**Yes, officially macOS-only** (15.0+ required), Swift-native, tied to ScreenCaptureKit + the Accessibility API — no Linux/Windows path in the primary repo. ([github.com/openclaw/Peekaboo](https://github.com/openclaw/Peekaboo))

Community rewrites exist but are early/unofficial and explicitly disclaim affiliation:
- **Windows:** [FelixKruger/PeekabooWin](https://github.com/FelixKruger/PeekabooWin) — "Windows-first rewrite of the practical desktop automation loop," JavaScript + PowerShell, does capture/OCR/click/scroll/type/window-manage; explicitly "not an official port and not affiliated with Peter's project."
- **Linux:** [nordbyte/PeekabooX](https://github.com/nordbyte/PeekabooX) — "Linux-first rewrite," Rust + Python, screen capture + "semantic desktop inspection" + input automation + plugins + MCP-ready agent APIs.

Both read as small/young community forks (no star/maturity signal comparable to the original) — **not safe as our production Linux/Windows path today**; worth re-checking in 6-12 months, not betting the ADR on now. ([WebSearch results](https://github.com/FelixKruger/PeekabooWin), [github.com/nordbyte/PeekabooX](https://github.com/nordbyte/PeekabooX))

### 4.1 What actually covers Linux/Windows/cloud today

1. **[trycua/cua](https://github.com/trycua/cua)** — "Open-source infrastructure for Computer-Use Agents. Sandboxes, SDKs, and benchmarks to train and evaluate AI agents that can control full desktops (**macOS, Linux, Windows**)." MIT-licensed, vertically integrated: sandbox provisioning (isolated VMs/containers so a rogue agent can't touch the host), an agent framework, benchmarking, and a macOS virtualization layer, all in one monorepo. 13.4k★/829 forks — the most credible **true cross-platform** computer-use stack, and it runs as sandboxed VMs rather than driving the bare host, which is actually a better safety property for an untrusted-agent test harness than Peekaboo's host-daemon model. ([github.com/trycua/cua](https://github.com/trycua/cua), [cua.ai](https://cua.ai/))
2. **[anthropics/claude-quickstarts/computer-use-demo](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)** — Anthropic's own reference agent loop for the Computer Use API: a Docker container running a **Linux desktop under X11 + VNC**, Streamlit control UI, driven by the Claude computer-use tool. Explicitly a "deliberately minimal, containerized reference" — not a maintained product, but the canonical starting point if we build a bespoke Linux/cloud computer-use runner ourselves (fork-and-extend rather than adopt-as-is). ([github.com/anthropics/anthropic-quickstarts](https://github.com/anthropics/anthropic-quickstarts/blob/main/computer-use-demo/README.md))
3. **[microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp)** (Apache-2.0, maintained by the Playwright team) — the natural **cloud/CI analogue**, but architecturally different from pixel-based computer-use: it feeds the agent Playwright's **accessibility-tree snapshot**, not screenshots, which the maintainers argue beats vision-based tools on speed, determinism, and token cost for *browser* surfaces specifically. This is closer to Peekaboo's own `see` AX-tree approach than to the Anthropic/cua pixel-click loop — worth noting both Peekaboo and Playwright converged on "read the accessibility tree, don't just click pixels" as the reliable primitive. ([github.com/microsoft/playwright-mcp](https://github.com/microsoft/playwright-mcp))

## 5. Evidence capture → our bundle format

Peekaboo has native primitives that map cleanly onto Proofbench's evidence bundle v2 `artifacts[]`/`checks[]` schema (see `PLAN.md` §5):

- **Stills:** `image`/`see --json` write PNGs plus a JSON sidecar (`ui_map`, `snapshot_id`, element list, capture-mode, perf metrics). → one `artifacts[]` entry per capture, `type: "screenshot"`, `provenance: "harness"` (Peekaboo, not the agent, took the pixels), `sha256` computed over the PNG, `meta` populated from the JSON sidecar.
- **Video:** the `capture` command supports `--video-out /path.mp4` for continuous recording, and a `capture live` mode that also emits a kept-frames directory + a `contact.png` contact sheet + `metadata.json` — i.e. it already produces a self-describing artifact folder, not just a raw file. → `type: "video"` artifact plus the contact sheet as a companion `type: "screenshot"` artifact (cheap visual index for the hub without needing to scrub video), both sha256'd. ([docs/testing/tools.md](https://github.com/openclaw/Peekaboo/blob/main/docs/testing/tools.md))
- **Structured UI-state checks:** the AX-tree JSON from `see` (element present/absent, label text, role) and the `analyze` vision-QA answer are exactly the kind of machine-checkable predicate our `checks[]` array wants (`"exists(ui_elements, label=='Save')"`, or an LLM-judged boolean from `analyze`) — feed them into `checks[].observed` / `expect`, not just attach as opaque files.
- **Proof-ladder placement:** a Peekaboo exploratory pass is inherently **L4 (effect-verified, UI probe)** territory — it's asserting real observed UI state, not just an exit code — and a scripted `peekaboo run` replay of the same script on every subsequent commit is what promotes a claim to **L5 (end-to-end observed, repeatable)**. This is the literal mechanism for PLAN.md's "one exploratory computer-use round → then build durable automation": the *first* round is `peekaboo agent "<natural language task>"` with `see`/`analyze` capturing evidence; if the user wants durable coverage, the harness **replays the same session as a `.peekaboo.json` script via `peekaboo run`** — Peekaboo's own snapshot/agent-trace mechanism already records the steps taken, so "explore once, then freeze into a repeatable script" is a feature Peekaboo has, not something we need to build from scratch on top of it.
- **Provenance:** since capture is a separate host-daemon/CLI process from whatever coding agent is under test, `provenance: "harness"` is honest by construction (unlike a screenshot the agent claims to have taken itself) — this directly satisfies PLAN.md's anti-fabrication requirement (§3 risk: "Agents game the evidence").

## 6. Ecosystem signal — this exact pattern is already validated by Peekaboo's own author

Peter Steinberger, on X, describing how he QA's OpenClaw itself: *"Been teaching codex to be my QA assistant. For every commit it creates a user-test scenario and uses webVNC (crabbox), computer/browser use (peekaboo/mcporter) to test OpenClaw like a user/QA person would. This runs in the background and opens PRs with fixes."* ([x.com/steipete/status/2061208638027395490](https://x.com/steipete/status/2061208638027395490))

This is close to a direct precedent for PLAN.md's proposed loop (agent proposes a test scenario per change → drives a real UI via computer-use → evidence → durable follow-up), from the person best positioned to know what works — worth citing in the ADR as external validation, not just internal design instinct. Also confirms the OpenClaw org's own toolchain shape: **crabbox** (remote box + webVNC) + **Peekaboo** (macOS computer-use) + **mcporter** (generic "call any MCP server" CLI/TS bridge, [github.com/openclaw/mcporter](https://github.com/openclaw/mcporter)) are used together, not as competing choices — mirrors our own substrate-polymorphic design (§2/§6 of PLAN.md: crabbox as remote-runner interop target, not a competitor).

## 7. ADR-ready recommendation

**Decision:** Adopt **Peekaboo** (MIT, `github.com/openclaw/Peekaboo`) as the **macOS local computer-use exploratory layer**, invoked as a **CLI subprocess** (`peekaboo agent "…" --json`, `peekaboo see/image/analyze --json`, `peekaboo run <script>.peekaboo.json`) from our harness/agent — not wired in as a standing MCP server. Map its capture artifacts (screenshot PNG + JSON sidecar, `--video-out` MP4, `capture live` contact sheets) directly into evidence-bundle-v2 `artifacts[]`, and its AX-tree/`analyze` output into `checks[]` predicates, tagged `provenance: "harness"`. Use its snapshot/script (`run` + `.peekaboo.json`) mechanism as the literal "freeze the exploratory pass into durable automation" step. For non-macOS substrates, do **not** adopt a Peekaboo clone; instead:
- **Cloud/CI browser surfaces:** Playwright + `microsoft/playwright-mcp` (already our stated cloud analogue in the task, and it's the maintained, Apache-2.0, accessibility-tree-based option — same underlying philosophy as Peekaboo's `see`).
- **Cloud/CI full-desktop (non-browser) surfaces, and any future Linux/Windows local need:** `trycua/cua` (MIT, true macOS/Linux/Windows, sandboxed-VM safety model) as the fallback, with Anthropic's `computer-use-demo` (Docker+X11+VNC) as the from-scratch reference if we ever need a bespoke minimal Linux runner instead of adopting cua's fuller stack.

**Alternatives considered:**
1. **Build our own macOS automation directly on Apple's Accessibility/ScreenCaptureKit APIs.** Rejected — Peekaboo already solved the hard parts (AX traversal limits/timeouts, ScreenCaptureKit perf, permission/daemon lifecycle, ScreenCaptureKit-vs-CGWindowList fallback) under an OSS-friendly MIT license and is actively maintained (releases days apart); reinventing this is pure sunk cost with no differentiation for us — our value is the *evidence schema and proof-ladder*, not screen-capture plumbing.
2. **Standardize on `cua` everywhere (including macOS local) for one codepath instead of two.** Rejected for now — `cua`'s safety model (drive a sandboxed VM) is right for an *unattended* cloud/CI computer-use runner, but the PLAN's local round is explicitly meant to run on **the developer's own live Mac** against their own real desktop state (dogfooding an actual dev environment, not a clean-room VM); Peekaboo is purpose-built for that, `cua` is not the sharpest tool for it (it would need to spin up a macOS VM). Keep `cua` as the *cloud/cross-OS* answer and Peekaboo as the *local macOS* answer — two purpose-fit tools, not one compromise tool. Revisit if `cua`'s macOS-host (non-VM) mode matures.
3. **Skip computer-use entirely and go straight to Playwright/scripted automation for every feature.** Rejected — it contradicts PLAN.md's explicit product requirement (one manual-style exploratory round before durable automation) and throws away the exact capability (natural-language `peekaboo agent`, AX-tree `see`) that lets an agent explore an *unfamiliar* UI change without a human first writing a selector-based script.

**Consequences:**
- We take a dependency on a young (v3.x, breaking changes as recently as the v3.0.0 rewrite), single-maintainer OSS project — pin the Peekaboo binary version per release, budget for CLI-flag churn, and design our invocation layer as a thin adapter (parse `--json` output into our own artifact/check types) so an upstream break doesn't ripple into our evidence schema.
- Local exploratory computer-use is **macOS-only at launch**; Linux/Windows engineers doing local dev either (a) get the browser-only exploratory round via Playwright MCP, or (b) don't get a local exploratory round at all until we build/adopt a `cua`-based local path for their OS — this is an explicit, documented gap, not a silent one.
- Because Peekaboo needs Screen Recording + Accessibility TCC grants and a live logged-in desktop session, it cannot run "headless" in most CI runners — this reinforces PLAN.md's substrate split: computer-use exploration is a **local/dev-machine** capability, cloud/CI verification leans on Playwright (browser) or `cua`/Anthropic-demo-style sandboxed VMs (full desktop), never bare Peekaboo in a CI container.
- CLI-first invocation (per §3) means near-zero standing context/latency cost when computer-use isn't needed that turn — aligned with our "ambient capture" design goal (PLAN.md P1) rather than an always-loaded MCP tool tax.

**Open questions:**
- Should our harness ship a *vendored/pinned* Peekaboo binary (reproducibility, matches our tested CLI-flag contract) or require the user to `brew install` it themselves (lighter footprint, but drifts out of pin)? Leaning vendor-pin given the release cadence.
- Is `peekaboo run`'s `.peekaboo.json` script format expressive enough to be *our* durable-automation artifact directly, or should we translate an exploratory Peekaboo session into a Playwright script instead (more portable, works in cloud CI too) and treat the Peekaboo script as disposable scaffolding? This determines whether "durable automation" for a macOS-native app feature stays Peekaboo-shaped forever or migrates to Playwright once the UI is a browser surface.
- `cua`'s exact API stability/pricing model (hosted cloud sandboxes vs. self-hosted) needs its own research pass before the P2/P3 roadmap items commit to it as the cross-OS fallback — flagged here, not resolved.
- Worth a direct outreach/PR to `openclaw/Peekaboo` (bundle-format interop) analogous to the crabbox interop plan in PLAN.md §8 — low cost, high goodwill, and Steinberger is clearly already receptive to "agent test evidence" framing (§6).
