Quickstart

This is a first pass verdict in about 5 minutes, using examples/basic — a minimal HTTP server with a /healthz endpoint and a POST /orders endpoint that appends to a JSON file. No Docker required. Every terminal block below is pasted from a real run — not a mockup.

Prerequisites

  • Go 1.23 or later
  • curl (used by the drive verb in the example)

Build pb

git clone https://github.com/launchwings/proofbench
cd proofbench
go build -o bin/pb ./cmd/pb
export PATH="$PWD/bin:$PATH"

A clean build prints nothing and exits 0 — no output is the expected output.

Step 1 — Bring the service up

cd examples/basic

ready.yaml in that directory declares how basic-orders comes up (go run . on port 8391), how to tell it's ready, and what to check. pb up starts it:

examples/basic
pb up --substrate local --manifest ready.yaml
up: basic-orders (local)

Step 2 — Wait for readiness

pb ready polls the probe declared in run.ready until it returns healthy or the timeout expires:

examples/basic
pb ready --manifest ready.yaml
ready: http :8391/healthz ok

Step 3 — Seed data

pb seed runs each step in seed[], in dependency order. examples/basic declares none, so it's an honest no-op rather than a silent skip:

examples/basic
pb seed --manifest ready.yaml
seed: no seed steps declared

Step 4 — Run a verification

examples/basic
pb verify --manifest ready.yaml --ticket ENG-001 \
  --claim "orders endpoint appends to orders.json"
{"status":"ok"}
{"status":"created"}
bundle: evidence/20260710-053442-verify
proof: L4
verdict: pass
note: 2 pass, 0 fail, 0 not-run
  [pass] up
  [pass] order-roundtrip

The two JSON lines are real, unedited output — the captured stdout of the up check's curl and the order-roundtrip drive verb's curl, streamed as the harness runs them. What follows is the verdict:

  • bundle: — the evidence bundle directory this run wrote under evidence/.
  • proof: — the highest proof-ladder rung this run reached (L4: a drive verb ran and an effect was observed — the order row landed in orders.json).
  • verdict: — pass, fail, or inconclusive, set last by the harness from the check results below it, never inferred from narration.
  • note: — a one-line tally (pass/fail/not-run counts); on a fail it also names the failing checks.
  • [pass] <name> — one line per check. A failing check prints a reason after an em dash — see when verify fails for a real example.

pb verify exits 0 only when every check passed and the verdict is pass; a non-zero exit means at least one check failed. The bundle is written either way — an honest fail is still evidence.

Step 5 — Read the bundle

pb report evidence/20260710-053442-verify

Prints the bundle as Markdown, ready to paste into a PR comment or ticket:

✅ **PASS** — orders endpoint appends to orders.json

proof level L4 · phase verify · substrate=local

| check | state | expect | observed |
|---|---|---|---|
| up | pass | http(http://localhost:8391/healthz)==200 | status=200 |
| order-roundtrip | pass | exitCode(order-roundtrip)==0 && rows(orders.json)>0 | exitCode=0; rows=1 |

**Artifacts**

- `up`, exit 0, 0.0s
- `order-roundtrip`, exit 0, 0.0s

---
`evidence/20260710-053442-verify` · run `20260710-053442-verify`

The underlying manifest.json in that same directory is the source of truth — every field in the report above (the expect predicate, the observed value, each artifact's SHA-256 and provenance) is read straight from it. See the evidence bundle format reference.

Bring it down

examples/basic
pb down --manifest ready.yaml
down: basic-orders (pid 51901) stopped

Clean up what the run wrote (the example's .gitignore already excludes these):

rm -rf evidence orders.json .pb
