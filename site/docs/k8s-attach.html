k8s-attach (BYOC)

k8s-attach is the fourth substrate: it never creates or deletes anything in a cluster (Shape-A, ADR-0011). pb up --substrate k8s-attach only asserts that the target pods are live and opens kubectl port-forward tunnels; pb down only kills the forwards it opened.

pb up --substrate k8s-attach --manifest ready.yaml
forward svc/appservice:8000 -> 127.0.0.1:54217
pb ready --manifest ready.yaml
ready tcp 127.0.0.1:54217 -> ok

One forward ... line per tunnel opened (one per unique locator — a resource and sources.k8s naming the same locator share a single tunnel), and one ready ... line naming the resolved probe and its outcome.

Naming the cluster context

Put a workspace.yaml next to your manifest naming the kubectl context and the granted namespace to forward into:

contexts:
  k8s-attach: "redcat@redcat"   # <kube-context>@<namespace>

Override at run time without editing the file:

export PB_K8S_CONTEXT=redcat
export PB_K8S_NAMESPACE=redcat

PB_K8S_CONTEXT / PB_K8S_NAMESPACE always win over workspace.yaml. From the real fixture (fixtures/k8s-attach/workspace.yaml): no cluster credentials live in this file (ADR-0008) — only a context name resolved from the local kubeconfig, plus a namespace.

services:
  appservice: /Users/prodigy/lyric/appservice
  metadata-service: /Users/prodigy/lyric/metadata-service

contexts:
  k8s-attach: "redcat@redcat"

Resource placeholders

resources.<name>.via.k8s names what to forward (e.g. svc/appservice:8000). pb up binds each to an ephemeral local port; reference the live forward anywhere in the manifest — probes, drive verbs, checks — with:

${resources.<name>.host}
${resources.<name>.port}

Env can also be derived from a live pod instead of a checked-in file:

run:
  local:
    env:
      derive:
        from: k8s-pod
        pod: "deploy/appservice"

Attach-only guarantee

k8s-attach is read/observe only: port-forward, read (kubectl get), and exec-based env derivation. It never applies, creates, deletes, or scales a cluster object.

requires-gating

Destructive actions a drive verb performs (firing an execution, writing a scenario doc) are the drive verb's own doing and must carry a gates[] entry — the substrate itself only opens tunnels. Checks that need an ID the harness can't fabricate (an execution ID, a scenario ID) declare it in requires; unset at verify time, the check records honest not-run rather than a hard fail or a fake pass. From the real ENG-17397 fixture (fixtures/k8s-attach/eng-17397-actions-controls.ready.yaml):

checks:
  - name: action-resolution
    level: L4
    exercise: "drive.read-execution"
    expect:
      - "jsonpath(execution.json,selectedAction)==$PB_EXPECTED_ACTION"
    requires: [PB_EXECUTION_ID, PB_EXPECTED_ACTION]

gates:
  - on: fire-execution
    reason: >-
      firing a note execution consumes cluster compute and mutates the
      executions/scenarios collections on a shared BYOC cluster — a human
      confirms the target scenario/sequence IDs before the run.
  - on: configure-action
    reason: >-
      writes scenarios.selectedNotesActions on a live scenario doc; confirm
      the scenario is a throwaway proof scenario, not a shared fixture.

In a real run, two L4 checks and the L5 Playwright check recorded honest not-run because PB_EXECUTION_ID was unset and a spec file hadn't landed yet — see the evidence bundle reference for the actual bundle. The proof level was reported at L3, not inflated.

Redeploy caveat

A port-forward pins to the pod(s) live when pb up ran. If the target rolls out (a new deploy, a pod restart) while forwards are open, the tunnel goes stale — the local port stays bound but the far end is gone. pb ready / pb verify will fail against a dead forward. Recover with:

pb down --manifest ready.yaml
pb up --substrate k8s-attach --manifest ready.yaml

There is no live re-attach yet; always cycle down/up after a rollout of anything you're attached to.
