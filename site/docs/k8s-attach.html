Attach your cluster (k8s-attach)

k8s-attach is the fourth substrate: the whole proof runs against a cluster you already deployed. pb up --substrate k8s-attach never creates, applies, deletes, patches, or scales anything (Shape-A, ADR-0011) — it asserts the target is live and opens kubectl port-forward tunnels so the harness's substrate-blind drivers and checks can dial 127.0.0.1:<port> exactly as they would against local or compose.

What attach-only means

Every kubectl invocation k8s-attach makes is one of exactly three read/observe verbs:

  • kubectl get — confirm a pod/deployment/service exists and is ready, read a service's own label selector, read a pod's container image digest(s).
  • kubectl port-forward — open one local-to-cluster tunnel per declared resource.
  • kubectl exec -- env — read a live pod's process environment, and only when the manifest opts in with env.derive.from: k8s-pod.

It never runs apply, create, delete, patch, or scale. Whatever a drive verb does against the cluster (firing an execution, writing a scenario doc) is the drive verb's own doing, not the substrate's — see gating destructive drive verbs below.

Prerequisites

  • kubectl on PATH, resolving to a working kubeconfig context. (k8s-attach unavailable: kubectl not found in PATH if it isn't.)
  • A namespace you're already granted get/port-forward/exec access to.
  • The target service already deployed and healthy — pb up asserts liveness, it never deploys anything.

Naming the cluster context

Put a workspace.yaml next to your manifest naming the kubectl context and the granted namespace to forward into:

contexts:
  k8s-attach: "redcat@redcat"   # <kube-context>@<namespace>

No cluster credentials live in this file (ADR-0008) — only a context name resolved from your local kubeconfig, plus a namespace. From the real ENG-17397 fixture (fixtures/k8s-attach/workspace.yaml):

services:
  appservice: /Users/prodigy/lyric/appservice
  metadata-service: /Users/prodigy/lyric/metadata-service

contexts:
  k8s-attach: "redcat@redcat"

Environment overrides

Override at run time without editing the file — these always win over workspace.yaml:

export PB_K8S_CONTEXT=redcat
export PB_K8S_NAMESPACE=redcat

If neither a workspace context nor PB_K8S_NAMESPACE resolves a namespace, pb up fails fast: k8s-attach: no namespace resolved (set PB_K8S_NAMESPACE or a workspace.yaml context 'name@namespace').

Resource placeholders and env derivation

resources.<name>.via.k8s names what to forward (e.g. svc/appservice:8000). pb up binds each to an ephemeral local port; reference the live forward anywhere in the manifest — probes, drive verbs, checks — with:

${resources.<name>.host}
${resources.<name>.port}

Env can also be derived from a live pod instead of a checked-in file:

run:
  local:
    env:
      derive:
        from: k8s-pod
        pod: "deploy/appservice"

Bringing it up and verifying

export PB_K8S_CONTEXT=redcat
export PB_K8S_NAMESPACE=redcat
pb up --substrate k8s-attach --manifest ready.yaml
pb ready --manifest ready.yaml
pb verify --substrate k8s-attach --manifest ready.yaml

One forward ... line prints per tunnel actually opened — a resource's via.k8s and sources.k8s naming the identical locator are deduplicated into a single tunnel rather than opening a redundant second one. One ready ... line names the resolved probe and its outcome; pb ready substitutes the forwarded 127.0.0.1:<port> addresses into the probe before polling, so the manifest's probe stays substrate-blind.

Gating destructive drive verbs

The substrate itself only opens tunnels. A drive verb that mutates cluster state (firing an execution, writing a scenario doc) must carry its own gates[] entry, and a check that needs an ID the harness can't fabricate (an execution ID, a scenario ID) declares it in requires — unset at verify time, the check records honest not-run instead of a hard fail or a fake pass. From the real ENG-17397 fixture:

checks:
  - name: action-resolution
    level: L4
    exercise: "drive.read-execution"
    expect:
      - "jsonpath(execution.json,selectedAction)==$PB_EXPECTED_ACTION"
    requires: [PB_EXECUTION_ID, PB_EXPECTED_ACTION]

gates:
  - on: fire-execution
    reason: >-
      firing a note execution consumes cluster compute and mutates the
      executions/scenarios collections on a shared BYOC cluster — a human
      confirms the target scenario/sequence IDs before the run.
  - on: configure-action
    reason: >-
      writes scenarios.selectedNotesActions on a live scenario doc; confirm
      the scenario is a throwaway proof scenario, not a shared fixture.

The real run, against redcat

The ENG-17397 Actions & Controls proof, attach-only against the redcat BYOC cluster:

redcat-cluster · k8s-attach
pb up --substrate k8s-attach --manifest ready.yaml
forward svc/appservice:8000 -> 127.0.0.1:56493
up: appservice (k8s-attach)
pb ready --manifest ready.yaml
ready: appservice ok
pb verify --substrate k8s-attach --manifest ready.yaml
bundle: evidence/20260710-010422-verify
proof: L3
verdict: pass
[pass] appservice-up
[not-run] action-resolution
[not-run] stage-progress
[not-run] stage-log-observed

Two L4 checks and the L5 Playwright check recorded honest not-run: PB_EXECUTION_ID was unset and the stage-log spec hadn't landed yet. The proof level was reported at L3, not inflated to match the manifest's highest declared check.

Pins: proving which build you tested

k8s-attach implements the optional Pinner capability: every bundle records the resolved k8s.namespace / k8s.context, plus each forwarded target's backing pod image digest, keyed image.<name>. A digest lookup resolves the concrete pod behind a locator (a service's own selector when it has one, else the app=<name> convention) and reads it with a read-only:

kubectl get pod/<pod> -o jsonpath='{range .status.containerStatuses[*]}{.imageID}{","}{end}'

A per-target lookup failure is skipped, not fatal — pins are best-effort provenance, and a missing pin is reported by its absence, never faked.

Teardown

pb down --manifest ready.yaml kills only the port-forwards this run opened, by recorded pid — it never deletes anything in-cluster. It removes .pb/k8s-forwards.json and then removes the substrate's own .pb directory only if that leaves it empty, so any other substrate/seed state left there is untouched. Down is idempotent: missing or already-stale forward state is not an error.

Troubleshooting: a forward dies mid-check

A port-forward pins to the pod(s) live when pb up ran. If the target rolls out — a new deploy, a pod restart — while forwards are open, the tunnel goes stale: the local port stays bound but the far end is gone. This doesn't crash pb; the next pb ready or pb verify surfaces it as a normal, named check failure pointing at exactly which check hit it, e.g.:

[fail] appservice-up — http :8391/healthz: connection refused

Recover by cycling the substrate — there is no live re-attach yet:

pb down --manifest ready.yaml
pb up --substrate k8s-attach --manifest ready.yaml
