Proof ladder

The proof ladder is the L0–L5 scale of verification depth every run must name, from L0 static-valid to L5 end-to-end observed. The rung reached is the run's proof level.

A report that doesn't name a rung isn't a proof. "Schema-valid" isn't "runs." "Exit code 0" isn't "effect verified."
L0static-validManifest parses and passes schema validation.
L1builds/loadsService binary or image builds without errors.
L2unit-greenUnit/integration test suite passed.
L3up+healthyService started and readiness probe returned healthy.
L4effect-verifiedA drive verb ran and a data/API/UI effect was observed.
L5end-to-end observedFull user journey exercised end-to-end and confirmed.

Why a ladder, not a checkbox

Proofbench encodes the builder-copilot lessons directly into the schema: schema-valid ≠ runs; wired ≠ runs. A rung is only reached when its evidence exists in the bundle — a check that records not-run does not silently count toward a higher level. Verify the effect, not the exit status; validate against the declared contract, not the tool's own report.

What earns each rung

  • L0 static-valid — ready.yaml parses and validates against spec/v0/ready.schema.json. Nothing has run yet.
  • L1 builds/loads — the service binary or image builds without errors.
  • L2 unit-green — the unit/integration test suite passed.
  • L3 up+healthy — pb up started the service and pb ready's probe (http/tcp/exec) returned healthy.
  • L4 effect-verified — a drive verb exercised a real product entrypoint and a check observed the resulting data/API/UI effect, not just an exit code.
  • L5 end-to-end observed — the full user-facing journey ran and was confirmed (e.g. a Playwright spec with screenshot/recording artifacts).

How the rung is set

Each check in ready.yaml declares the level it proves. When pb verify runs, every declared check appears in the evidence bundle's checks[] with a tri-state result:

pass fail not-run

The bundle's proofLevel is the highest rung whose checks all passed — a single not-run or fail at a level caps the reported rung below it. A run that only proves L3 reports L3, even if an L5 check exists in the manifest but couldn't execute. See the evidence & provenance reference for a real bundle where three checks are honestly not-run while the reported proof level stays at L3.

Exit code / verdict relationship

The proof level and the bundle's verdict (pass / fail / inconclusive) are set together, last, from the checks — never inferred from the harness's own exit status or the agent's narration. A bundle that cannot reach its declared check's level records the blocking check as not-run with a reason and sets verdict: inconclusive, not pass. In CI, the GitHub Action's own exit code follows the bundle's verdict, not pb's raw process exit status.

Example report

pb verify
pb verify --manifest ready.yaml --ticket ENG-001 --claim "orders endpoint appends to orders.json"
bundle: evidence/20260704-101500-verify
proof: L4
verdict: pass
[pass] up
[pass] order-roundtrip

Two L3/L4 checks both passed, so the report names proof: L4 — the highest rung actually reached, stated plainly next to the verdict, never "done."
