the pipeline is the argument

Five entries. One real sequence.

Every run passes through the same ledger — a manifest declares it, the harness runs it, and the bundle records what actually happened.

№1

Manifest

How a service becomes runnable and testable — deps, seed, health probe, drive verbs, checks — declared once in ready.yaml.

checks:
  - name: order-roundtrip
    level: L4
    exercise: drive.create-order
    expect:
      - "exitCode(order-roundtrip)==0"
      - "rows(orders.json)>0"
№2

Bring-up

The harness starts the service the manifest declares — a local process, Docker Compose, or a port-forward into your own cluster.

$ pb up --substrate local --manifest ready.yaml
starting basic-orders (local)
№3

Drive

A drive verb exercises the real product entrypoint — never a look-alike, never a curl one-liner standing in for the app.

drive:
  create-order:
    run: ./scripts/create-order.sh
    identity: env:USER_EMAIL
    output: json
№4

Evidence

Every command is captured — exit code, log, a SHA-256 — and tagged with who produced it: the harness, never the agent.

{
  "type": "command", "name": "03-fire",
  "sha256": "a3f1c2...",
  "provenance": "harness",
  "meta": { "cmd": "./scripts/create-order.sh", "exitCode": 0 }
}
№5

Verdict

Set last, after every check and artifact is in — never inferred from the agent's own narration.

"verdict": "pass",
"note": "set last, from artifacts"

the proof ladder

Every run names the rung it reached.

A report that doesn't name a level isn't a proof. "Schema-valid" isn't "runs." "Exit code 0" isn't "effect verified."

L0static-validManifest parses and passes schema validation.
L1builds/loadsService binary or image builds without errors.
L2unit-greenUnit/integration test suite passed.
L3up+healthyService started and readiness probe returned healthy.
L4effect-verifiedEarns it: a drive verb ran and a data/API/UI effect was observed.
L5end-to-end observedEarns it: the full user journey exercised and confirmed.

agent proposes, harness proves

Verdicts are set last — by the harness, never the agent.

The bundle records who produced each artifact. A check the agent merely narrated is never mistaken for one the harness ran and captured.

before you attach a cluster

Questions worth answering upfront.

Is my cluster safe to attach?

k8s-attach is attach-only (Shape-A, ADR-0011): it port-forwards and reads. It never runs kubectl create or kubectl delete, and never applies, creates, deletes, or scales a cluster object.

Do you store my credentials?

Never. Per ADR-0014, the headless-agent adapter inherits whatever auth the customer already has — subscription token, API key, or Bedrock/Vertex credentials — with zero Proofbench involvement. Cluster access works the same way: a kubeconfig context name, never a stored secret (ADR-0008).

What agents work with Proofbench?

Any of them. Bring your own genuine CLI — Claude Code, Codex, Gemini — or speak to pb mcp serve over stdio MCP from any MCP-capable agent.

What happens when a check can't run?

It records honest not-run with a reason — never a silent pass and never a fabricated fail. A bundle that can't reach its declared level sets verdict: inconclusive, not pass.

What's the license?

Apache-2.0. The evidence bundle format is open and portable — export your data any time.
