open-source · agent-verification harness

Your agents say it works. Proofbench proves it.

The agent only ever proposes. A deterministic harness disposes — it conjures your app (builds and boots a disposable copy from the exact commit), runs the agent-proposed walk (the scripted user actions) in a real browser, taps the datastore out of the agent's reach, and seals the evidence (signs it, so any later edit is detectable). The agent cannot write the verdict, fabricate the evidence, or touch the seal.

That record is real: n8n PR #9157, a webhook fix. The same user walk ran on the fix and on the build just before it. On the older build the submission never reached the store — the page said "Error in workflow" and the out-of-band store tap confirmed nothing persisted. Verdict: DOES NOT WORK, failure reproduced 2 of 2. With the fix: WORKS, reproduced 2 of 2. That differential is The Catch.

agent proposes · harness disposes

The asymmetry is the whole game.

An agent's unreliability can only ever cost you a WORKS — it degrades to COULD NOT DETERMINE. It can never manufacture a false WORKS. That is the one property Proofbench is built to hold.

The agent proposes

Fallible and revisable: how to read the sentence, which user actions to try, the narration. Proposed once, then frozen before the walk runs.

The harness disposes

Authoritative: it executes the walk, records ground truth out of the agent's reach, seals the evidence with a real ed25519 key, and computes the verdict by fixed rules.

Uncertainty is CND

Never rounded up to green. A failure must reproduce (kFail ≥ 2) to convict; a one-off is "observed once, could not reproduce" — recorded, never a verdict.

the pipeline is the argument

Five entries. One real sequence.

Every run passes through the same ledger. The seam phases run on your infra; the trust phases — seal and verdict — are ours, and not swappable, because a swappable seal would just relocate the lie.

№1

Recipe → Promise

A recipe.json names the code identity (merge + parent SHA), how to bring the system up, and the front door. The agent compiles the intent into a promise, then it is frozen.

{
  "intent": "a visitor submitting the form
             persists an execution",
  "code_identity": { "merge": "3ddc176",
                     "parent": "869b8f14" }
}
№2

Conjure a fresh world

The harness builds the system from the pinned tree and brings it up hermetically — a disposable world per leg, torn down by a deadman's switch whatever happens.

fingerprint (harness):
  sha:          3ddc176dfa2d…
  image_digest: sha256:bcf698a7…
  version:      1.11.0
№3

Drive the front door

The agent-proposed walk goes in as a stranger — no deep links. It reads the page, types, submits. Every DOM step is captured as a tool-provenance receipt.

browser-drive (tool):
  navigate → introspect → type
  → click submit → observe
  "Form Submited / Your response
   has been recorded"
№4

Tap the store · seal

Out of the agent's reach, the harness reads the store of record before and after, then a fresh session re-reads the same id. Everything is content-addressed and sealed.

store-delta (harness):
  execution_entity.max_id 0 → 1
fresh-execution (tool, fresh session):
  observed id 1  (binds the delta)
EVIDENCE SEALED ed25519
№5

Verdict, set last

A deterministic truth-table judges the sealed receipts — never the agent's narration. Only tool|harness receipts can satisfy a claim; a WORKS needs a confirmed effect reproduced k ≥ 2.

verdict: WORKS
  1 confirmed effect claim
  all claims satisfied
  reproduced k=2

the magic moment

The Catch: the PR is why it works.

A single WORKS proves nothing — the feature might have worked before your change. So Proofbench runs the identical agent-proposed walk on the merge and on its parent and reports the differential. It passes only when the merge WORKS and the parent does not. Four real recipes have run this, across three different stacks — the sealed evidence for each is linked below.

three answers, never two

WORKS is earned. The other two are honest.

A binary pass/fail forces a lie whenever the truth is "I couldn't tell." The tri-state is the scope valve — it always says which, always with the receipt.

WORKS

A confirmed effect on the store of record, bound to a fresh out-of-band re-read, reproduced across ≥ 2 fresh worlds. Never from a single walk.

DOES NOT WORK

The walk ran and the promised effect went missing — and the failure reproduced (kFail ≥ 2). A defect in the change, shown as the broken moment.

COULD NOT DETERMINE

The harness couldn't bring the system up, reach the state, or bind the code identity — so it will not say WORKS. Names what blocked it, and the fix.

every claim carries its receipt

Provenance is ranked. Only the harness can satisfy.

Each receipt is stamped with who produced it. A receipt the agent handed in is forced to agent provenance and content-addressed on the way in — it can corroborate, but it can never satisfy a claim on its own.

harness store taps, seals — out of the agent's reach tool the browser drive, fresh-session reads agent narration — corroborates only, never satisfies

  "id": "store-delta", "kind": "delta",

  "sha256": "457dd672c113afdf…",
  "data": { "entity": "execution_entity.max_id",

The whole bundle is signed with a real ed25519 key over a canonical digest of intent + claims + receipts + verdict. Edit one byte anywhere and the seal breaks. The case file re-derives all of it in your browser, offline — no server, no network.

install honestly, in under a minute

On npm. npx it, or clone for recipes.

proofbench is published on the npm registry with a pb bin — no clone needed to run the honesty gate. The npm package ships only the engine (src/); the example recipes/ and fixtures/ don't ship, so authoring recipes or running the shipped examples still needs a clone. The repo's default branch predates this rewrite and is historical only — clone product-v1 explicitly, as below.

npx proofbench gate

pb gate is the E1 malicious-driver honesty gate — deterministic, Docker-free, network-free, seconds. A PASS is your install smoke test. To author recipes or run the shipped examples, clone instead:

git clone -b product-v1 https://github.com/0prodigy/proofbench.git
cd proofbench
node src/cli.mjs gate

Full recipe-authoring path (Docker + an agent, a real sealed verdict in under an hour): docs/getting-started.md.

pb-integration-v1

One recipe schema. One resolution point.

A recipe selects its substrate through four fields — conjure.mode, code_identity.mode, store_tap.engine, and drive.mode — and src/registry.mjs is the single point that resolves each field to its provider; an unrecognized value fails loudly, never a silent fallthrough. Docker (run or compose) is the one substrate pb ships today. A new substrate — Kubernetes included — earns its way into the registry only by passing an executed live verdict, never ahead of one. Full contract, adapter shape, and the --json/exit-code surface: docs/integration.md.

before you point it at a PR

Questions worth answering upfront.

How can the agent not just fake a WORKS?

The agent only proposes the walk and the narration — both frozen before execution. The harness executes, taps the store of record out of the agent's reach, and computes the verdict by fixed rules. Receipts the agent hands in are forced to agent provenance, and only tool|harness receipts can satisfy a claim. Structurally, the worst the agent can do is downgrade a WORKS to COULD NOT DETERMINE.

Why run the parent commit too?

Because a WORKS on the merge alone doesn't prove your change is why it works — the feature might predate it. The differential re-runs the identical walk on the parent SHA. It only passes when the merge WORKS and the parent doesn't, so the PR's diff is the thing being credited.

What does the seal actually prove?

It is tamper-evident: a real ed25519 signature over a canonical digest of the bundle, so any post-seal edit is detectable and the case file self-verifies offline. It is not tamper-resistant — on your own machine the key and run live on hardware you control, so a box owner can forge at rest. Every case file states this ceiling in its honesty panel.

Does it need my API key or credentials?

The proposer runs on the customer's own agent. By default it shells out to the locally installed claude binary and inherits whatever subscription auth is already there — no API key required, and credentials never pass through Proofbench.

What's the license?

Apache-2.0. The evidence bundle format is open — the case file is one self-contained HTML file you can archive and re-verify forever.
